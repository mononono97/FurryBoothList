# 위키 작성 규칙

이 프로젝트의 작업은 모두 이 위키(`docs/wiki/`)에 기록합니다. 사람이든 Claude든
작업을 마칠 때 아래 규칙대로 문서를 함께 갱신합니다.

## 위치와 이유
- 위치: 저장소 안의 `docs/wiki/` 폴더 (Markdown 파일)
- GitHub 저장소 Wiki 대신 이 폴더를 쓰는 이유: 문서 변경이 코드 변경과 같은 PR에
  함께 들어가서 리뷰하고 되돌리기 쉽고, GitHub에서 파일을 열면 바로 렌더링되어 보입니다.
- GitHub에서 보는 법: 저장소 → `docs/wiki/Home.md`

## 언제 무엇을 쓰나
| 상황 | 할 일 |
|---|---|
| 새 기능 추가 | `기능-<이름>.md` 새로 만들고 [Home](Home.md) 목록에 추가 |
| 기존 기능 수정 | 해당 기능 문서의 "변경 기록"에 한 줄 추가, 본문 설명도 최신 동작으로 고침 |
| 여러 단계로 진행되는 큰 작업 | `작업-<이름>.md`를 만들어 목표·결정 사항·진행 상황을 적고, 끝나면 결과 요약 |
| 모든 작업 공통 | [변경 이력](변경-이력.md)에 날짜·내용·PR/커밋 한 줄 추가 |

## 문서 형식
- 한국어로 씁니다.
- 파일명은 한글 가능, 띄어쓰기 대신 `-` 사용.
- 기능 문서는 다음 순서를 따릅니다.
  1. **무엇을 하나**: 사용자 입장에서 보이는 동작
  2. **왜 이렇게 했나**: 결정 이유, 버린 대안
  3. **어떻게 구현했나**: 관련 함수·상수·localStorage 키 (`index.html`의 이름 그대로)
  4. **확인 방법**: PC 브라우저에서 직접 확인하는 절차
  5. **변경 기록**: `YYYY-MM-DD 내용 (커밋 또는 PR 링크)`
- 날짜는 항상 절대 날짜(YYYY-MM-DD)로 씁니다.
- 비밀번호, API 비밀키 같은 민감 정보는 적지 않습니다.
  (Firebase 웹 설정값은 원래 공개되는 값이라 예외)

## 작업 흐름
1. 브랜치에서 작업 (main에 직접 푸시하지 않음)
2. 코드 변경과 위키 갱신을 같은 PR에 포함
3. PR 설명은 한국어로, 변경 내용·이유·확인 방법을 적음
4. 기존 기능(우선순위 정렬, Google 로그인 동기화, 메모·방문 상태·예산)이 깨지지 않았는지
   변경 전후로 확인하고 결과를 PR에 적음
